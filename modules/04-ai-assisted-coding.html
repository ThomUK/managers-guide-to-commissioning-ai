Module 4about 5 minutesPart A: Using it

AI-assisted code development

You need this if you manage people who write code or analysis, or you are asked what “AI coding tools” change.

Relies on module 3: an agent is a model working in a loop, using tools behind permission gates.

The key idea

AI coding tools are agents whose tools are a code editor and a command line. The human’s job moves from typing to specifying, reviewing and testing.

What changes

An AI coding tool is an agent, as in module 3, whose tools are a code editor and a command line. It can read the files in a project, change them, run them and react to what happens. The person’s work moves from typing code to saying clearly what is wanted, reviewing what comes back and testing that it works. In the walkthrough above, the person wrote one sentence and read two changed lines. The agent did everything in between, including finding and correcting its own mistake.

Where it helps and where it needs supervision

These tools are strongest on work that is well specified, testable and routine; on finding their way around unfamiliar code; and on first drafts. They need close supervision where requirements are ambiguous, where a change is security-sensitive, and anywhere there are no tests. Without tests nobody, human or agent, can easily tell whether a change is right.

A useful test is whether the task could be handed to a capable new colleague with a short written brief. If the brief would be hard to write, the agent will struggle for the same reason.

What makes it safe

Two long-standing practices do most of the work. Version control records every change, so anything the agent does can be inspected and undone. Automated tests give a quick, repeatable check that the code still behaves as intended. With both in place, an agent’s mistakes are cheap to catch. Without them, they are easy to miss. It also helps to keep each task small, so that the change a person must review stays short enough to read properly.

Review remains a human responsibility. An agent reporting success is evidence, not sign-off.

What this means for your decisions

  • Productivity gains depend on good specifications and good tests; invest there.
  • Accountability does not move: the person who merges the change owns it.
  • Decide which repositories, data and commands the tools may use, as in module 3.
The detail your technical team handles optional

Context limits on large codebases

A large codebase does not fit in a context window. The agent searches for the relevant files and reads only those, so its work is only as good as its search. Clear structure and documentation help agents for the same reason they help new staff.

Where the code is sent

Whatever the agent reads is sent to wherever the model runs. The four arrangements in module 2 apply to code exactly as they do to any other data.

Licensing and secrets

Teams need a position on the licence status of generated code, and on keeping passwords and access keys out of anything the agent can read. Neither is new; both matter more when more code is written faster.

Coding agents on a local model

A coding agent can be pointed at an open model on your own hardware, which keeps the code on site. Smaller local models are generally weaker at long, multi-step tasks, so teams test before relying on them. Part B explains the hardware side.
